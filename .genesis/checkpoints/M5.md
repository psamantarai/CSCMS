## What shipped
- **Backend** (`backend/app/auth.py`): `GET /api/auth/bootstrap` (unauthenticated status
  check, `{needed: bool}` from `COUNT(*) FROM users`), `POST /api/auth/bootstrap` (creates
  the first admin user, `begin_write()` before the count guard so two concurrent first-run
  submits can't both pass it, 409 + no write once a user exists, shop name written to
  `settings` on the same call, returns a session token so the wizard logs the operator in).
- `backend/app/seed.py`: `run_seed()` no longer creates the admin user (a standing
  `admin`/`admin123` row would make bootstrap's zero-users precondition never true on a real
  fresh install) — reference data only now (Cash Drawer account, services, settings).
  `seed_admin_user()` split out as a separate, test-only helper for the ~24 backend tests
  that need a user row.
- `backend/app/accounts.py`: `_system_user_id()` now looks up the first admin by `role`
  instead of a literal `username = 'admin'`, since bootstrap lets the operator pick any
  username.
- **Frontend**: new `src/pages/Setup.tsx` — two steps, `CreateAdminStep` (shop name +
  username/password/confirm, calls `useAuth().bootstrap()`) → `ShopSetupStep` (repeatable
  account-name/type/opening-balance rows via the existing `POST /accounts`, no backend
  change needed there). `src/lib/auth.tsx` gained `bootstrap()` alongside `login()`, same
  token+user shape. `src/App.tsx` gates on a `bootstrap-status` query (`enabled: !user`)
  with a sticky `inSetup` boolean — documented deviation below.
- Tests: 4 new in `test_auth.py` (status needed/not-needed, create+login+shop-name-trimmed,
  409-reject-creates-nothing), 2 new in `test_seed.py` (`run_seed` creates no user,
  `seed_admin_user` idempotent + hashes). Every other backend test file's `_seeded_conn`
  helper picked up an explicit `seed_admin_user(conn)` call since `run_seed()` no longer
  provides one.

## Documented deviation from PLAN.md wording
`docs/PLAN.md` 9.8.2 says the frontend checks "zero users (and separately, zero accounts)."
The actual code only checks zero-users (via `/auth/bootstrap`'s `needed` flag), because
`run_seed()` unconditionally creates a Cash Drawer account — `accounts.length === 0` is
never true on any real install, seeded or not, so re-deriving the gate from account count
would skip Setup's step 2 the instant `bootstrap()` logs the operator in. The `inSetup`
state is set once when `bootstrap-status` first reports `needed: true` and stays true
(sticky) until the wizard's `onComplete` fires, rather than being re-derived every render.
Explained in a comment on the hook in `App.tsx`; functionally verified below.
